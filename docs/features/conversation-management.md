# 工作区与对话管理

## Sub-features

M01 工作区分组与接续，M02 搜索与重命名，M03 归档与恢复，M04 忙碌与并发，M05 桌面宽度与手机导航，M06 观察释放，M07–M08 删除，M09 存储预算与清理，M10 未读与跨端同步。

## How to get to it (user POV)

登录后从侧栏进入。已登记工作区各自显示最近的对话及独立的「显示更多」，对话行前的状态点表示运行中、完成未读（标题加粗）、失败、等待、待核实或已中断。工作区标题可收起列表，收起后标题旁汇总该组需要关注的状态；「在 X 新建对话」直接进入该工作区草稿，首次发送才创建对话。仍保存有对话的旧工作区可在「未登记工作区」找到，能否继续执行取决于其原生连接配置。标题搜索在侧栏的「搜索与跳转」（⌘K / Ctrl+K，手机在标题栏）；归档对话在侧栏底部的「已归档」页；已移除工作区的对话在「设置 › 工作区」。

## Driving it with Harness

使用[共同入口](README.md)准备隔离 fixture 或真实 Harness。所有标题和消息均使用合成内容。开始前记录被测版本、每段对话的 hash 和所属工作区。测试归档或恢复前记录目标身份，操作后从列表重新打开，再以同源快照和 `inspect` 独立核对历史和原生身份。

| 场景 | 动作和判据 |
| --- | --- |
| M01 分组与旧对话 | 用「＋」在 Fixture A 依次进入草稿，以七条不同的短唯一文本首次发送，每段都用 `complete` 收尾；首条文本成为初始标题。Fixture B 在未使用时显示「暂无对话」。点击 A 的「显示更多」，核对初始六段仍在、首段追加出现，打开首段并核对原历史、选中项与 hash。仅阅读时顺序不变；向首段发送被接收的消息后它移到组首。失败发送不应置前。折叠 A 后正文保持。再用 B 的「＋」检查草稿工作区为 B，首次发送后核对归属。 |
| M02 搜索与重命名 | 刷新使 A 恢复默认列表。在「搜索与跳转」中搜索首段标题，核对结果所属工作区和 hash。点「管理对话」并保存新的中文标题，第二个页面只用新标题能找到这段对话。用两个不同的搜索词快速切换，最终结果只匹配最后的输入。 |
| M03 归档与恢复 | 在已就绪且无未决操作的对话行打开「管理对话」并点「归档对话」。侧栏和「搜索与跳转」中消失。在侧栏底部「已归档」页搜索、打开旧历史并核对 hash，正文显示归档提示及「恢复对话」。保留 root 重启应用，确认仍可在归档视图找到。点正文的「恢复对话」，在弹出的「管理对话」里再点「恢复对话」（也可从标题栏「对话操作」进入），之后在主列表打开，再发送一条消息，用原生身份、历史与调用次数确认接续。fixture 先验证产品路径，Codex 与 DSH 原生分支各核对一次。 |
| M04 忙碌与交错 | 发送后等 fixture 显示运行中再尝试归档，应保留主列表入口并提示原因。再用两个页面从已就绪对话同时发起发送和归档，记录两端动作与结果。如果发送先接收，归档应被拒绝。如果归档先保存，新发送被拒绝且输入保留。分别用真实 Harness 核对其等待输入状态，前提缺失时标记受阻。 |
| M05 宽度与移动端 | 创建足够长的标题，核对侧栏没有被标题撑宽，行操作可点。桌面拖动分隔线，刷新后核对测得宽度，聚焦分隔线用左右方向键调整。缩窄窗口验证正文可操作。在手机从「打开对话导航」抽屉和标题栏「搜索与跳转」走通搜索、归档恢复及返回正文。窄视口只证明布局与操作路径，真实设备单独记录。 |

### 生命周期与删除验证

M06：在两个页面打开同一已完成对话，再关闭一个、随后关闭全部。真实 Host 上通过原生调用记录核对同一对话共享观察；fixture 的 inspect 没有观察计数，只能看到页面每 15 秒的 `/reading` 续期，共享观察与释放由下面的协议回归覆盖；结束阅读且没有执行责任后解除观察，不继续每 5 秒读取正文。顺序阅读超过 16 段历史仍能继续打开；运行中的对话关页后继续，重新打开保留原身份与结果。阅读租约每 15 秒续期，失联 45 秒后回收；这不是任务超时。协议回归运行 `node --test test/workbench.test.ts`。

M07：在空闲 Codex 对话的管理窗口点击「删除对话」，核对标题、工作区、Harness 和不可恢复提示；先取消，确认历史仍在，再次进入并确认。删除完成后列表、搜索、另一页面正文和旧链接均不再展示该内容。通过原生独立读取和中书资源检查验证清理，工作区文件及其他对话保持。当前 Codex adapter 提供原生删除；DSH 仅提供归档恢复，不显示删除入口；直接请求其删除接口（带 CSRF 的 `POST /api/private/workbench/conversations/<id>/delete`，正文 `{"confirm":true}`）也应返回 409 `conversation_delete_unsupported`，并保留历史及绑定。fixture 的 Codex 删除从自己的 native.sqlite 清除正文；DSH 替身即使具备测试删除能力也不能绕过产品限制。可用 `node test/support/feature-fixture.ts inspect-deletions --root "$zh_verify_root"` 独立检查仅含身份和结果的调用记录；它不能替代真实 Host 验证。

fixture 可用 `node test/support/feature-fixture.ts reject-delete-next --root "$zh_verify_root" --title '本轮唯一标题'` 在适配器边界注入一次拒绝；标题取原生 inspect 的精确值，不能把中书重命名后的标题当原生标题。

M08：在运行、排队或未知状态尝试删除，应拒绝并保留可到达对话。空闲删除请求丢失响应或应用在原生清理后中断时，以同一对话再次删除/重启，核对持久阶段恢复和幂等结果。当前删除日志不保留正文，原生已完成后本地清理可独立恢复；失败的原生步骤可从管理入口重试。回归运行 `node --test test/conversation-deletions.test.ts test/workbench.test.ts`。本节是执行方法，不代表每个真实原生分支已取得证据。

### 存储预算与清理

M09：中书数据库有实例预算（`ZHONGSHU_STORAGE_BUDGET`，默认 16 GiB；fixture 用 `serve --storage-budget`）。用较大预算启动隔离 fixture，在一段对话的输入框加入三张合成图片，每张不超过 2 MiB（例如 1.9 MiB，超过会被拒绝；上传即计入，草稿里移除图片不会立刻释放预算，未关联的上传 7 天后回收）；以相同 root 改用 `--storage-budget 4MiB` 重启。侧栏「设置」带“存储已满”徽标，打开设置的「存储」标签后核对用量、预算、各类别（上传与快照图片、可清理的图片缓存）和“已达到预算上限”说明；没有缓存时“清理图片缓存”不可用，并提示删除不再需要的 Codex 对话或调高预算。再验证：

- 再加入一张图片被拒绝，提示存储已满且文件保留；在另一工作区草稿首次发送被拒绝，内容保留且列表不出现新对话。伪造的上传和创建请求同样返回 `storage_budget_reached`。
- 在已有对话只发送文字（不带新图片）照常被接收；阅读、停止、归档不受影响。
- 删除该 Codex 对话（M07 路径）后，存储页与侧栏徽标在列表刷新后（约 1 秒内）回到正常比例，新建对话恢复可用。图片缓存的清理（只删除可从原生重新取回的图片副本，不动上传和工作区图片快照）由 `node --test test/storage.test.ts` 覆盖；真实原生图片缓存需在有原生图片的对话上另行核对。

80% 起侧栏「设置」旁出现提醒点，「设置 › 存储」显示“已用超过预算的 80%”。预算按数据库实际使用的页面计算，删除后立即释放，不等待整理；数据库文件本身不会自动缩小。原生自己的会话文件不在此统计，也不作为拦截条件。

### 未读与跨端同步

M10：未读由服务端记住（[architecture](../architecture.md)），两个登录端看到同一结果。用两个独立浏览器上下文（不是两个标签页）分别登录同一 fixture。端 A 在一段对话发送唯一消息，等「运行中」后打开侧栏「设置」（设置页覆盖正文，不算在看）；端 B 停在空白首页。执行 `node test/support/feature-fixture.ts complete --root "$zh_verify_root" --title '本轮标题'`。两端在不刷新的情况下都应显示：该行绿点且标题加粗、标签页标题「(1) 中书」；两端都会弹出「「标题」已完成」提示，几秒后自动消失；在端 A 的提示消失前点「查看」打开对话。改由端 B 先打开该对话：端 A 的绿点与标题计数应在数秒内消失。反例：正在打开且可见的对话完成时任何一端都不出现未读；在运行中的对话点「停止当前轮」后立即切到另一段对话，停止造成的中断不算未读；另一段对话用 `fail --title …` 结束时显示红点并计入未读。只看同一浏览器的两个标签页不能证明跨端；真实手机由用户在测试实例上验收。

协议与存储回归：`node --test test/workbench-store.test.ts test/workbench.test.ts test/workbench-http.test.ts` 覆盖结果键、阅读租约标记、后台标签页不误标、迁移基线与 `/attention` 排序计数。

## Gotchas

搜索只查标题。旧对话和归档结果从服务端查询。主列表按最近被接收的用户消息的提交时间排序；没有消息时按创建时间排序，侧栏宽度保存在当前浏览器。归档对话的历史仍可读，新提交必须先恢复。
每个工作区、搜索结果和归档列表先显示有限条目，「显示更多」只读取下一页并追加；已展开窗口收到变更时从首部补齐和去重，收起的工作区及搜索时隐藏的工作区暂停刷新。验证大量数据时，在隔离实例准备合成对话，统计每次展开的列表请求与行数，并从搜索打开尚未加载的旧标题。另一页面移动或删除分页边界记录后继续展开，验证不依赖边界记录仍存在，且结果没有重复或永久漏项。

## Implementation and regression

- [侧栏与管理表单](../../src/web/conversation-navigation.tsx)负责宽度、分组与对话行，[搜索与跳转](../../src/web/workbench-search.tsx)负责标题搜索与未读读取，[归档页](../../src/web/archive-view.tsx)与[设置页](../../src/web/settings-view.tsx)负责各自入口，[工作台](../../src/web/workbench.tsx)负责打开对话、草稿、提示与标签页标题。
- [私有路由](../../src/server/workbench-http.ts)约束输入并沿用登录与 CSRF，[生命周期岗](../../src/server/workbench/lifecycle.ts)核对原生状态，[存储](../../src/server/workbench-store.ts)保存标题和归档标记，并在提交入队时检查归档状态。
- `node --test test/workbench-http.test.ts test/workbench-store.test.ts` 覆盖查询分页、迁移、认证与归档竞态。独立运行证据按[共同要求](README.md#独立执行验收)记录。
- 存储预算：[storage.ts](../../src/server/storage.ts) 计量与淘汰，[资源](../../src/server/resources.ts)区分上传与可再生副本，[设置页存储面板](../../src/web/storage-status.tsx)；`node --test test/storage.test.ts`。

Codex 等待输入的协议回归可用 `node --test test/codex-workbench.test.ts` 复跑。测试对端通过本地 socket 返回原生等待标志，归档请求应返回 409，读回仍为未归档。测试对端结束等待后，同一请求应成功。真实 Codex 等待状态需另行触发并记录。
