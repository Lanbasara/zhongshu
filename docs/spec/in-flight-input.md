# 运行中排队与追加输入

## 目标与范围

用户在 Agent 运行时可以为同一对话安排后续工作，也可以把其中一条提前交给 Harness。依据为 2026-11-03 对齐中用户确认的队列分层与两种提前发送意图。首版覆盖多条排队、逐条提前发送和回执核对。整队提前发送、回答提问和处理审批另行对齐。

## 用户行为

| 动作 | 可观察结果 |
| --- | --- |
| 排队 | 运行中默认排队。同一对话可连续加入多条消息，入队后仍可继续输入。未派发的条目可编辑或删除，页面刷新或换端后可找回。当前轮正常完成后，队列按加入顺序逐条派发，每条作为该对话的新一轮。 |
| 追加到本轮（Codex） | 选中一条待派发消息，将其绑定到点击时看到的活动轮。该轮已结束或换轮时，保留原条目并提示用户决定下一步。保留的条目须等用户重新选择发送方式，才可派发。 |
| 尽快发送（DSH） | 选中一条待派发消息，立即交给 Harness，优先让正在运行的轮消费。若发送途中该轮结束，允许在同一对话开启或进入后续轮。中书在取得原生证据后显示实际送达的轮次。 |

例如队列依次有 A「补测试」、B「先别改公共接口」、C「总结变更」。点 B 的提前发送操作只提交 B，A 和 C 保持相对顺序。若 B 已到达 Harness，但尚无证据表明它进入哪一轮，界面显示接收状态，实际轮次待核实。

## 分层与恢复

- Workbench 持有每个对话的队列，统一处理持久化、排序、编辑、删除、派发和回执核对。Adapter 声明支持的发送能力，负责原生调用和结果映射。界面按声明显示动作。对话配置和原生执行权沿用 [Harness 边界](../adr/0001-native-harness-boundary.md#接入模块与两个-adapter)。
- 条目有稳定身份，同一次操作沿用原操作编号。自动派发和手动提前发送必须竞争同一条目的派发权。界面区分中书已入队、Harness 已接收和已核实归属轮次。响应丢失时核对原操作，禁止自动重发可能已被接收的消息。遵循[操作恢复约定](../adr/0004-recoverable-communication.md#跨通道成立的契约)。

## 验收

- 分别在两个真实 Harness 的运行中从浏览器排入三条带独立标记的消息。刷新或换端核对顺序，编辑一条、删除一条、再补一条。当前轮正常完成后，从原生历史核实保留条目按顺序各出现一次、各自开启新轮，编辑前文本和已删除条目未送达。
- 用受控工具等待保持活动轮，从队列提前发送中间一条，核对原生历史中它只出现一次且属于当前轮，其余条目仍按原顺序等待。另用单条消息验证轮尾竞争，在点击提前发送后、原生接收前结束原轮。Codex 保留条目供用户决定，原生历史无此消息。DSH 的后续轮中有且只有一条对应消息，界面显示该轮。两端均核对原对话绑定和配置。
- 在自动与手动派发竞争时核对同一条目只交付一次。在原生接收后丢弃回执，再刷新或换端核对，同一操作恢复到实际归属轮次，原生历史只有一份消息。HTTP 回执和模型自述不足以证明送达轮次。
- 实现后更新[执行功能地图](../features/execution.md)，按[共同入口](../features/README.md#独立执行验收)取得独立执行证据，并通过仓库四项检查。轮尾竞争与配置继承沿用[接入实验](integration-probes.md#两个-harness)。

## 暂停与恢复

- 主动停止、运行失败或 Codex 错过目标轮时，保留并暂停剩余队列。用户选择“继续派发”后按原顺序派发，或单独选择条目提前发送。
- 排队沿用普通输入的图片与引用格式。入队时验证资源归属，派发前重新核对。排队内容失效时保留条目供用户处理。
