# 架构：边界与演进

本文记录当前结构及其理由。工作约束见 [AGENTS.md](../AGENTS.md)，开发与集成见 [开发文档](development.md)。

## 当前系统

当前只有一条公开的前后端连通链路，没有业务数据、身份系统、持久化或 Agent 执行能力。

```text
浏览器页面 ──同源 HTTP──→ Node 服务
                          ├─ 固定公开静态资源
                          └─ 健康与构建版本 API

源码 ──构建──→ dist ──打包──→ 镜像 ──外部发布流程──→ 运行实例
```

| 边界 | 当前入口 | 设计理由 |
|---|---|---|
| 页面与服务 | [浏览器资源](../src/public/) / [HTTP 服务](../src/server.mjs) | 同源接口使构建不依赖真实域名；服务端控制公开能力范围 |
| 源码与产物 | [构建脚本](../scripts/build.mjs) / [Dockerfile](../Dockerfile) | 将版本信息嵌入产物，使运行结果能够关联源码提交 |
| 产品与运行环境 | [Compose](../compose.yaml) / [配置示例](../.env.example) | 可配置的运行契约支持不同部署目标，本地开发不需要生产凭据 |
| 产品与发布运维 | 通用镜像及自动化接口 | 源码交付可追溯产物；具体实例的发布、权限与运维知识由操作者在仓库之外维护 |

目前前后端由一个服务、一个镜像交付，足以验证完整链路，并减少尚无实际需要的运维边界。Node 原生实现是当前规模下的选择，不限制后续采用适合需求的框架。

Web manifest 提供独立窗口入口；离线和后台能力尚未实现。个人 Agent 工作台是演进方向，不代表相关能力已经存在。

## 架构如何成长

**局部理解。** 模块的接口应让调用者理解用途、输入输出、失败与副作用，而无需先通读其内部实现。相关规则集中维护，依赖与资源归属清楚；目录和模块数量服从这个目标。

**真实边界。** 当变化理由、信任边界或生命周期开始不同时，再考虑分离。提取抽象应能说明它简化了什么当前问题，以及增加了什么成本。先让一个完整行为成立，再据反馈调整结构。

**显式契约。** 穿越进程、信任或持久化边界的信息需要明确契约与校验。产品逻辑通过明确接口使用环境能力；运行数据的生命周期独立于程序升级。

**可观察的变化。** 设计新能力时同时考虑如何运行、判断成功、定位失败，以及必要时如何恢复。诊断信息应帮助定位问题并保护敏感内容。

## 维护决定

改变重要边界时，在对应说明中留下问题、决定、理由与影响；计划明确标为计划，落地后更新当前状态。用代码和配置链接承接可直接查询的细节。

当独立决定的背景已使本文难以阅读时，再拆出决策记录并从这里链接。修订决定时保留仍有解释价值的取舍，移除失效指引；无需为每个实现细节建立文档。
