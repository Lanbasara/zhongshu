# 通用验证能力

从 [feature-map](features/README.md)选择本次要证明的行为；本文提供准备现场和留存结果的方法，不替验证者预先决定所有场景或通过结论。

## 选择表面

| 要判断什么 | 使用的表面与前提 |
| --- | --- |
| 页面入口、输入、反馈、阅读与恢复 | 当前源码构建的真实浏览器页面；HTTP/数据库读回作为独立事实 |
| 原生执行、上下文、配置、停止 | 上述页面连接已登录的真实 Harness；两个 adapter 分别记录结果 |
| 丢回执、乱序、长历史、慢端等受控边界 | 实际应用与可控网络或原生替身；说明替换的位置，不能据此签发真实 Harness 兼容性 |
| 管理员命令、备份与构建产物 | 实际 CLI、临时数据目录与实际产物；容器边界使用真实 Compose |

当前仓库提供[行为测试](../test/)与[容器检查](../scripts/check-container.mjs)，尚无通用浏览器故障注入/原生替身启动器。需要时在仓库外准备最小现场；测试内 fake 不是可直接交给浏览器的运行服务。没有可控的故障前提就记录缺口，不用随机断网声称复现了特定派发窗口。

## Launch：独立现场

先读[开发流程](development.md)与本次功能页。确认使用的源码、Node 版本、端口、数据目录和原生连接；同时只启动一套本次验证现场。正在供用户试用的实例不是可销毁的测试夹具。使用新的数据目录、合成工作区和自己的浏览器上下文；目录分离不等于操作系统沙箱。

以下从仓库根目录运行，示例端口须先确认空闲；占用时另选端口。`ZHONGSHU_DATA_DIR` 在初始化前设置，避免误用默认管理员数据：

```sh
npm ci --ignore-scripts
zh_verify_root="$(mktemp -d "${TMPDIR:-/tmp}/zhongshu-verify.XXXXXX")"
chmod 700 "$zh_verify_root"
export ZHONGSHU_DATA_DIR="$zh_verify_root/data"
export HOST=127.0.0.1 PORT=4391
export ZHONGSHU_ORIGIN="http://127.0.0.1:$PORT"
export ZHONGSHU_ALLOW_HTTP_LOOPBACK=true
unset ZHONGSHU_HARNESS_CONFIG
npm run admin -- init
REVISION="$(git rev-parse HEAD)" npm run build
node dist/server/main.js
```

管理员初始化使用真实终端的不回显输入；自动化可用 CLI 的 `--password-stdin` 从临时秘密通道提供随机测试密码。密码、Cookie、CSRF 和原生连接秘密不进入命令参数、截图、日志或 PR。保留本次终端/进程的归属，应用以前台方式运行，另一个终端或浏览器做检查。

以上不连接 Harness，适合私人入口和版本检查。原生功能按 [Harness 接入](harnesses.md)准备本次独立工作区、已授权的原生 Host 与受保护配置，然后在启动应用前显式设置 `ZHONGSHU_HARNESS_CONFIG`。原生安装、登录与监管由操作者提供；登录缺失时请求人工完成，不读取其他实例的账号文件。记录实际原生版本和选定配置，不默认使用用户的活动对话。只验证一个 adapter 时，将另一个记为未覆盖。

## Doctor：确认准备好了

- 请求本次 origin 的 `/api/health`，应为 `status: ok`；读取 `/api/version`，与本次构建关联。这两项通过不证明登录或 Harness 可用。
- 打开本次 origin，确认登录页、登录和工作台。创建对话前检查正常配置接口 `/api/private/workbench/configuration` 或页面的工作区、模型、权限和连接状态；缺失前提不等于功能通过。
- 保存仓库、base、HEAD、未提交 diff 摘要、构建标记、时间与环境。构建标签不是内容证明；有未提交改动时同时保留补丁身份，构建后再次改代码需重建。运行证据不能跨版本借用。

## Drive：由本次问题组合场景

功能页给出用户入口、前提及独立观察点；通过页面完成正在验证的用户动作，CLI/API 用于准备与读回。按当前可访问名称定位，不保存易失的元素编号。等待具体状态或内容，超时保留最后事实；单纯等待固定秒数或收到 HTTP 200 不算通过。

需要查网络时只保存无秘密的路径、状态码、时间和必要的合成字段，避免原样导出带凭据的 HAR。需要原生身份或磁盘结果时通过受控的只读诊断确认；模型说“已写入”“已停止”不是独立证据。

修改前后运行适用的[基础检查](development.md#决定怎样验证)和功能页所列回归；测试名及限制以实际测试源码为准。用户可见的验收仍由本次真实路径给出。

## Evidence：版本、观察和结论

证据放在源码之外的本轮目录或任务/PR/CI 附件；源码只维护可复用方法。每个结论至少包含：功能/子能力、预期、实际动作与观察、内容身份、环境/真实或替身边界、证据位置、清理状态。

- `PASS`：本内容和环境下，所选路径实际运行且观察符合预期。
- `FAIL`：路径已运行，保存预期与实际不符的证据。
- `BLOCKED`：尝试被具体前提阻止，说明缺少的工具、登录或服务。
- `UNCOVERED`：本轮未运行的分支、设备或环境。

报告按子能力和环境给结论；测试全绿、服务 ready、历史 PR 通过或用户说“测试好了”都不能自动扩大为整项功能通过。Android、TLS/代理、负载与性能按[质量要求](quality.md)单独取证。

## Cleanup：只清理本次拥有的资源

停止本次应用终端/进程；核对端口已释放，关闭自己创建的浏览器标签与故障注入，清理自己的合成材料。只对可核实归属的原生 Host 和受控工具做清理：停止应用、停止原生轮次与工具进程退出是不同事实。保存所需证据，敏感数据库和登录材料继续按私有数据保护；未确认归属时报告残留，不按端口或模糊进程名批量杀进程。

若用户明确要求保留试用环境，按交接要求保留，记录归属及启停入口；单次验证不借此清理用户原有实例。现场准备方法漂移时修正本文或操作者外部 capability，行为驱动变化时修正对应功能页。
