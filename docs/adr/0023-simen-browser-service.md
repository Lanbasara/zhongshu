# 司门：Agent 共用的浏览器

> 草案。标"用户已定"的是用户的决定，其余是 Agent 的提议，等用户确认。

## 背景与依据

Agent 用浏览器主要做两件事：检查自己生成的 HTML 渲染得对不对（电脑和手机宽度、控制台报错、截图），以及在别的办法都不行时去操作网页。取数据仍然靠各自的工具和接口。

问题出在并发上。Agent 通过 chrome-devtools 或 Playwright 这类工具用浏览器，每个工具各自启动一个浏览器，数量不受控。在小主机上，几个浏览器就能把内存和 CPU 吃满，拖垮中书和 Harness。

用户的判断（2026-11-09）：
- 只解决这一个问题：Agent 共用一个自己管理的浏览器，窗口数量、排队、CPU 和内存都受控，功能和平常用的浏览器工具一样全；
- 浏览器始终用同一个档案，登录状态保留下来（用户已定）；
- 通用能力，不为任何具体网站写代码，也不限制访问哪些网站（用户已定）；
- 不做给人看的界面；
- 名字叫「司门」，命令是 `simen`；在司辰之后单独一批做（用户已定）。

核实过的事实。实验在一台 2 核 8 GB 的 Linux 主机上做，用的是 Debian 12 的 Chromium 156，跑在容器里，容器限制为内存 1.5 GB、CPU 1 核、只读根文件系统。

- **资源**：
  - 空闲时约 180 MB；同时开一个本地报告和三个常见的行情网页，约 590 MB；关掉其中三个后回到约 270 MB。
  - 重页面主要耗 CPU：一个要 12 秒；两个同时开要 19 秒，和一个接一个开差不多。所以窗口不用多。
- **不开端口也能遥控**：用 `--remote-debugging-pipe` 启动后，能完成平常要用的所有操作：开页面、导航、执行脚本、截图、设置设备尺寸、点击、输入中文。
- **渲染**：装上 Noto CJK 和 emoji 字体后，中文和 emoji 正常显示；手机宽度下的横向溢出和控制台错误都能测出来。
- **沙箱**：在默认的容器安全策略下，Chromium 自带的沙箱起不来。在 Codex 容器策略的基础上，再允许 `chroot` 和带命名空间的 `clone`/`unshare`，就能带着沙箱运行。
- **登录状态**：带有效期的 cookie 重启后还在；只在会话期内有效的 cookie，要打开"继续上次浏览"才能保留。
- **档案锁**：浏览器被强行结束后，档案里会留下一把锁，换了容器后 Chromium 就拒绝启动。服务启动时要先清掉这把旧锁。
- **认出对话**：DSH 运行 shell 命令时会设置 `DSH_SESSION_ID`（见 [ADR 0022](0022-sichen-time-module.md)）。

## 决定（提议）

1. **一个小模块「司门」，命令 `simen`。** 做法和司辰一样：
   - 有独立的目录和协议版本；
   - 命令行只用 Node 自带的库；
   - 出错时用中文说明，加 `--json` 时输出给程序读的格式；
   - 跟着中书一起构建和更新。
2. **一个实例只有一个浏览器，放在单独的容器里，有硬上限。**
   - 内存、CPU、进程数由实例限制，建议 1.5 GB、1 核、512 个；
   - 用一个持久档案（用户已定），浏览器能只读地看到工作区，用来打开本地 HTML；
   - 一个小宿主程序负责启动浏览器：开始时清掉旧锁，打开"继续上次浏览"，崩溃后重新启动。
3. **窗口和排队。**
   - **上限**：窗口数由实例配置，默认 2 个。
   - **归属**：一段对话最多占一个窗口，靠 `DSH_SESSION_ID` 认出，这段对话后面的命令都接着用它。
   - **排队**：窗口满了就先来先得；命令行会显示前面还有几个，最多等 5 分钟，之后明确失败。
   - **收回**：闲置 3 分钟收回；有人在排队时，一次占用超过 15 分钟也会收回。
4. **命令和平常用的浏览器工具一样全**：
   - `open`：打开网址或工作区里的文件；
   - `snapshot`：读页面文字和带编号的可操作元素；
   - `click`、`fill`、`press`、`scroll`：按编号或选择器操作；
   - `eval`：在页面里执行脚本；
   - `shot`：截图；
   - `viewport`：切换电脑或手机预设，也可以写宽×高；
   - `console`：看控制台报错；
   - `close`、`status`、`doctor`。
5. **磁盘用量有上限。**
   - 服务自己不保存截图或页面。截图只在 Agent 要的时候生成，存到 Agent 指定的位置，和它写的其他文件一样。
   - 浏览器缓存设上限（建议 100 MB），档案只放登录状态和设置。
   - 镜像大小固定，不会随着使用增长。
6. **路径简单，不开遥控端口。**
   - `simen` 命令连到宿主程序：宿主只在本机回环上监听，并要求令牌；
   - 宿主再通过管道控制 Chromium，不开浏览器的遥控端口。这样 Agent 只能走 `simen`，不会绕过排队另开浏览器。
   - 中书的应用不经手这条路径。
7. **首批只接 DSH。** Codex 要先核实它怎么认出对话、沙箱里能不能联网，然后再接。

## 取舍与后果

- **为什么不直接给 Agent 浏览器 MCP 工具：** 数量控制不了；MCP 调用认不出是哪段对话（见 ADR 0022），几段对话会抢同一个页面。
- **为什么不用现成的浏览器服务（如 browserless）：** 它按连接分配会话，做不到"一段对话连续用一个窗口"；它的许可证也有限制。
- **同一个档案、不限网站的代价：** 所有窗口共用登录状态，Agent 在已登录的网站上就等于用户本人，用户接受这一点。实例备份里也会带着这份档案。
- **为什么放开两项系统调用：** 浏览器打开的是不可信的网页，要保留 Chromium 自己的沙箱，不用 `--no-sandbox`。
- **成本：** 每个环境一份约 1.5 GB 的镜像；运行时最多占 1.5 GB 内存和 1 核 CPU。Chromium 要跟着安全更新走。
- **不做：** 给人看的浏览器界面、远程操作画面、针对具体网站的处理。
