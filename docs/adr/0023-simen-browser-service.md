# 司门：中书共享的浏览器服务

> 草案。用户已经定下的内容都标了"用户已定"，其余是 Agent 的提议，等用户确认。

## 背景与依据

浏览器在中书里是一项通用的兜底能力，有两类用途：

- 核验 Agent 生成的 HTML，比如电脑和手机宽度下会不会横向溢出、控制台有没有报错，并截图；
- 别的办法都不行时，在网页上操作，比如由用户亲手登录、通过人机验证。

取数据仍然靠各自的工具和接口（例如见微），浏览器不替代它们。

现成做法是给每个 Agent 一个浏览器工具，比如 chrome-devtools 或 Playwright 的 MCP。这些工具各自启动浏览器，数量不受控。在小主机上，几个浏览器就能吃满内存和 CPU，拖垮中书和 Harness。

用户的判断（2026-11-09）：
- 中书要有一个自己管理的浏览器服务：控制窗口数量和排队，控制性能与并发，功能要全；
- 浏览器始终用一个独立的档案，保留登录状态（用户已定）；
- 它是通用能力，**不为任何具体网站写专门的代码**（用户已定）；
- 不限制登录哪些网站（用户已定）；
- 名字叫「司门」，命令是 `simen`（用户已定）；
- 在司辰之后单独一批做（用户已定）。

核实过的事实。实验环境是一台 2 核 8 GB 的 Linux 主机，用 Debian 12 自带的 Chromium 156。浏览器跑在容器里，限制为：内存 1.5 GB、CPU 1 核、根文件系统只读、去掉全部 capability。

- **资源**：
  - 空闲时约 180 MB；
  - 同时开着一个本地报告和三个常见行情网页，约 590 MB；关掉三个后回到约 270 MB；
  - 重页面加载主要耗 CPU：单个重页面要 12 秒；两个同时加载用了 19 秒，和一个接一个加载的总和差不多。所以 1 核上限下，多开窗口只能让大家不用互相等，并不会更快。
- **不开端口也能遥控**：用 `--remote-debugging-pipe` 启动后，能新开页面、导航、执行脚本、截图、设置设备尺寸、推送画面、点击鼠标、输入中文，不监听任何网络端口。
- **渲染**：装好 Noto CJK 和彩色 emoji 字体后，中文和 emoji 显示正常；手机宽度下的横向溢出和控制台错误都能测出来。
- **沙箱**：在默认容器安全策略下，Chromium 自带的沙箱起不来。在 Codex 容器策略的基础上，再允许 `chroot` 和带命名空间标志的 `clone`/`unshare`，就能带着沙箱运行。
- **登录状态**：
  - 带有效期的 cookie，浏览器重启后还在；
  - 只在会话期内有效的 cookie 默认会丢；打开档案偏好里的"继续上次浏览"（`restore_on_startup`）后，也能保留。
- **档案锁**：浏览器被强行结束后，档案里会留下一把锁，上面记着旧主机名。换了容器后，Chromium 会拒绝启动。独占档案的服务启动时，要清掉这把旧锁。
- **人机验证**：有的网站对机房地址弹出滑动验证，去掉自动化标记也照样弹，只能由人亲手完成。
- **登录窗口小样**：小样只有一个页面。浏览器把画面推给它，它把点击、滚动、文字和按键传回浏览器；从 Mac 经 SSH 隧道连到 VPS 实测：
  - 画面一帧约 17 KB；页面不动时不发画面，操作时每秒约 50 KB；
  - 从点击到看到画面变化约 0.1–0.5 秒，输入文字约 0.3 秒，回车后新页面约 0.6 秒出现；
  - 点中搜索框、输入中文、回车出结果页，整个流程走得通；换成手机宽度后，远端也跟着变成手机尺寸。
  - 还要打磨的地方：手机高清屏上画面偏糊；改变尺寸后要刷新页面；拖动、输入法组字、复制粘贴要逐项处理。
- **认出对话**：DSH 运行 shell 命令时会设置 `DSH_SESSION_ID`（见 [ADR 0022](0022-sichen-time-module.md)）。Codex 的程序里有 `CODEX_THREAD_ID`，但运行时是否设置，还没核实。
- **端口风险**：中书的 Agent 工具端点和 Harness 在同一台机器的回环上互通。浏览器的遥控端口如果也开在回环上，Agent 就能绕过司门直接控制浏览器，还能一次读出全部 cookie。

## 决定（提议）

1. **独立模块「司门」，命令 `simen`。** 做法和司辰一样：
   - 有自己的目录和协议版本，命令行只用 Node 自带的库；
   - 命令按"类别 + 动作"组织；
   - 出错时用中文说明，加 `--json` 时输出给程序读的格式；
   - 跟着中书一起构建和更新。
2. **通用，不为具体网站写代码。** 司门只提供通用的浏览器操作，不包含任何针对具体网站的规则、选择器或绕过手段。
3. **浏览器是独立的原生服务，不放进中书的镜像。**
   - 一个实例只有一个浏览器进程、一个持久档案；
   - 档案只在浏览器服务那边，不在任何工作区里，Agent 读不到档案文件；
   - 浏览器能只读地看到工作区，用来打开本地 HTML。
4. **只用管道遥控，不开端口。** 浏览器那边运行司门的一小段宿主程序：
   - 它用 `--remote-debugging-pipe` 启动 Chromium，再通过一个 unix socket 把这条通道只交给中书；
   - Agent 只能走 `simen` → 中书 → 宿主这一条路；
   - 宿主还负责清掉旧锁、打开"继续上次浏览"，以及浏览器崩溃后重新启动。
5. **窗口和排队由中书管。** 中书知道是哪段对话在调用，也知道这一轮什么时候结束。
   - **上限**：窗口数按实例配置，建议默认 2 个。
   - **归属**：一段对话最多占一个窗口，靠 `DSH_SESSION_ID` 认出；同一段对话的连续命令都用这个窗口。
   - **排队**：窗口满了，先来先得。命令行会显示前面还有几个；等太久（建议 5 分钟）就明确失败，不会无限等下去。
   - **收回**：那段对话这一轮结束时收回；闲置超过 3 分钟收回；有人在排队时，单次占用超过 15 分钟也收回。
   - **重启**：浏览器重启后所有占用作废，命令行会说明要重新打开。
6. **资源有硬上限。** 浏览器服务的内存、CPU 和进程数由实例限制，建议 1.5 GB、1 核、512 个进程。超出时只影响浏览器自己。
7. **功能要全。** 首批命令：
   - 打开：`open`，可以是网址，也可以是工作区里的文件；
   - 查看：页面文字，以及带编号的可操作元素清单；
   - 操作：`click`、`type`、`press`、`scroll`，按编号或选择器定位；
   - 执行脚本：`eval`；
   - 截图：`shot`，图片写到命令所在的目录；
   - 尺寸：`viewport`，可选电脑或手机预设，也可以写宽×高；
   - 其他：`console`、`close`、`status`、`doctor`。
8. **登录窗口，由用户亲手操作。**
   - 中书网页里有一个只有管理员能打开的「浏览器」页面。页面上显示浏览器推来的实时画面，用户的点击、滑动、输入和改网址再传回浏览器。电脑和手机都能用。
   - 它占一个窗口，排在 Agent 的队伍前面。
   - 画面只在有人看、页面在变的时候才传。
   - 司门不自动破解验证码，也不替用户输入密码。
9. **不限制网站（用户已定）。** 后果写在下面"取舍与后果"里。
10. **安装与体检。**
    - Chromium 版本固定在浏览器服务的镜像里，随实例一起更新；
    - `simen doctor` 和实例体检会报告浏览器版本、窗口、排队和内存。
11. **首批只接 DSH。** Codex 要先核实它的对话编号，以及沙箱里能不能联网，然后再接。

## 取舍与后果

- **为什么不直接给 Agent 浏览器 MCP 工具**：数量控制不了；MCP 调用认不出是哪段对话（见 ADR 0022）；遥控口暴露在外。
- **为什么不用现成的浏览器服务（如 browserless）**：它按连接分配会话，连接一断会话就结束，做不到"一段对话连续用一个窗口"；它的许可证也有商用限制。
- **只用一个档案、不限网站的代价**：
  - 所有窗口共用登录。用户登录过的网站上，Agent 能做用户本人能做的事；网页里的内容也可能诱导 Agent 去做。用户接受这个后果。
  - 档案会进入实例备份，备份里也就带着登录凭据。
- **为什么排队放在中书里**：中书能按"这一轮结束"收回窗口，宿主可以保持简单。
- **为什么放开容器策略里的几个系统调用**：浏览器打开的是不可信的网页。宁可放开两项系统调用，也要保留 Chromium 自己的沙箱，不用 `--no-sandbox`。
- **更新负担**：浏览器服务的镜像约 1.5 GB，Chromium 需要跟着安全更新走。
- **登录窗口的工作量在打磨上**：核心通路已经用小样跑通，难的是手机上的清晰度、输入法、拖动和延迟。
