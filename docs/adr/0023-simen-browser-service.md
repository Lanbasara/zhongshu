# 司门：Agent 与 Chrome DevTools 之间的中间层

> [ADR 0026](0026-shared-agent-capabilities.md) 将司门接入 Codex，继续使用实例共用的浏览器与窗口配额。

## 背景与依据

Agent 用 Chrome DevTools 操作浏览器，用来检查自己生成的 HTML，或在别的办法都不行时去操作网页。问题是，每次使用都可能新开一个浏览器，数量不受控。小主机上几个浏览器就能吃满内存和 CPU，把中书和 Harness 拖垮。

用户的判断（2026-11-09，用户已定）：
- 做一个夹在 Agent 和 Chrome DevTools 之间的中间层，只解决并发和资源问题；
- 最多一个浏览器、两个窗口；一段对话最多占一个窗口，其他的排队，最多等 5 分钟；闲置 5 分钟后收回；
- 浏览器像人用自己的浏览器一样：登录过的网站下次打开还是登录状态，Agent 用时不做任何区分或清理；这只是浏览器自己的数据目录，不是专门准备的登录档案（用户 2026-11-09 说明）；不限制访问哪些网站；
- 通用能力：不为具体网站写代码，也不做给人看的界面；
- 名字叫「司门」，在司辰之后单独一批做。

核实过的事实：
- **官方工具（读代码核实）**：用的是 Google 的 chrome-devtools-mcp 1.12，Apache-2.0 许可。
  - 它自带命令行：`chrome-devtools <工具> <页面编号> …`。背后有一个常驻的后台进程，还附有写给 Agent 的官方使用说明。
  - `--browserUrl` 可以连到已经开着的浏览器。
  - 默认要求页面类工具带上页面编号，并按编号分派（`pageIdRouting`），本来就是为多个 Agent 共用一个浏览器设计的。
  - 后台进程没在跑时，命令会自己启动它；如果没给 `--browserUrl`，它还会自己再开一个浏览器。浏览器越开越多，就是这么来的。
  - 截图如果没指定保存位置，就存进系统临时目录，每次新建一个子目录，它自己从不清理。
- **DSH**：DSH 的 MCP 连接由所有对话共用，调用工具时不带对话身份（见 [ADR 0022](0022-sichen-time-module.md)）。shell 命令带 `DSH_SESSION_ID`，能认出是哪段对话。
- **容器实验**：在 2 核 8 GB 的主机上用 Debian 12 的 Chromium 156 测试，容器限制为内存 1.5 GB、CPU 1 核。
  - 资源：空闲约 180 MB；开一个本地报告加三个常见行情网页，约 590 MB。重页面主要耗 CPU，两个同时加载并不比先后加载快。
  - 沙箱：在 Codex 容器策略的基础上，再允许 `chroot` 和带命名空间的 `clone`/`unshare`，Chromium 自己的沙箱就能运行。
  - 字体：装上 Noto CJK 和 emoji 字体后，中文显示正常。
  - cookie：带有效期的 cookie 重启后还在；只在会话期内有效的 cookie，要打开"继续上次浏览"才能保留。
  - 档案锁：浏览器被强行结束后，档案里会留下旧锁，下次启动前要先清掉。

## 决定（用户 2026-11-09 确认）

1. **司门是中间层，不另造浏览器操作。**
   - 实例上，Agent 运行的 `chrome-devtools` 命令就是司门。写法和官方完全一样，Agent 照官方说明使用即可。
   - 司门先检查窗口规则，再把命令原样交给官方命令行执行，输出也原样返回。
   - 官方工具的所有能力都直接可用，跟着官方版本更新。
2. **每个实例绑定唯一一个浏览器（用户已定）。**
   - 浏览器由实例创建，实例配置告诉司门它在哪里；司门只连这一个，不用用户自己的浏览器。
   - 不同实例（例如预发和正式）各有各的浏览器和档案，互不相通。实例可以不接浏览器，这时司门会明确说明没有可用的浏览器。
   - 浏览器单独放在一个容器里，有硬上限：建议内存 1.5 GB、CPU 1 核。
   - 浏览器始终用自己的同一个数据目录（用户已定），不做清理；能看到工作区，用来打开本地 HTML。
   - 一个小启动程序负责：清掉旧锁、打开"继续上次浏览"、浏览器崩溃后重启。
   - 官方后台进程只有一个，由司门启动并连到这个浏览器。司门不让官方工具自己再开浏览器。
   - **用时才开，不用就彻底回收（用户已定）。** 有对话要窗口时才启动浏览器和官方后台进程；最后一个窗口关闭或收回后，两者都退出，内存和 CPU 全部释放，只留一个很小的启动程序等下次调用。登录状态存在档案里，重启后还在。
3. **窗口规则（用户已定）。**
   - 最多 2 个窗口；一段对话最多占 1 个，靠 `DSH_SESSION_ID` 认出。
   - `new_page` 时分配窗口。窗口满了就排队，先来先得，最多等 5 分钟。
   - 已经有窗口的对话再 `new_page` 会被拒绝，并提示它接着用自己的窗口。
   - 用到别的对话的页面编号会被拒绝。
   - `close_page` 立刻释放窗口；闲置 5 分钟的窗口由司门关掉、收回。
4. **磁盘有上限。**
   - 每段对话的临时文件（例如没指定位置的截图）放在司门管理的临时目录里，窗口收回时一起删除。
   - 浏览器缓存设上限，建议 100 MB。
   - 司门自己不保存任何页面或截图。指定了 `--filePath` 的截图，存在 Agent 指定的位置。
5. **安装与体检。**
   - 官方工具的版本固定在镜像里。
   - 司门跟着中书一起构建（做法同司辰），放进 DSH 的 PATH。
   - 中书给 Agent 的说明里写明：用浏览器时运行 `chrome-devtools`。
   - `chrome-devtools doctor`（司门加的）会报告浏览器版本、窗口和排队情况。
6. **首批只接 DSH。** Codex 要先核实它怎么认出对话、沙箱里能不能联网，然后再接。

## 取舍与后果

- **为什么包的是官方命令行，而不是官方 MCP 工具：** MCP 认不出是哪段对话，做不到"一段对话一个窗口"；命令行能认出。
- **为什么不自己实现浏览器操作：** 官方工具已经很全，自己做既重复，又要一直追着维护。
- **遥控口开在本机回环上：** Agent 绕过司门直接连浏览器是做得到的。我们接受这一点：司门防的是无意中越开越多，不防恶意；浏览器有硬上限，即使被绕过，也拖不垮 VPS。
- **同一份浏览器数据、不限网站的代价：** Agent 在已登录的网站上就等于用户本人，用户接受这一点。这份数据里有网站的登录凭据，所以不进实例备份，恢复备份也不会动它（实现时定，2026-11-09）。
- **为什么放开两项系统调用：** 浏览器打开的是不可信的网页，要保留 Chromium 自己的沙箱，不用 `--no-sandbox`。
- **成本：** 每个环境有一份约 1.5 GB 的浏览器镜像，外加官方工具包约 14 MB。没人用时只剩一个很小的启动程序；用的时候，浏览器最多占 1.5 GB 内存和 1 核 CPU，另有一个官方后台进程。第一次用要多等浏览器启动的那一两秒。
- **不做：** 给人看的界面、针对具体网站的处理、自造的浏览器命令。
