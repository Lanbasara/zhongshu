# 司门：中书共享的浏览器服务

> 草案。用户已定的只有三条，标了"用户已定"：名字、保留登录、在司辰之后单独一批。其余是 Agent 的提议，等用户确认。

## 背景与依据

Agent 需要浏览器的场景：
- 核验生成的 HTML 报告：电脑和手机宽度下会不会横向溢出、控制台有没有报错，并截图；
- 读要靠脚本才出内容的网页；
- 在用户已登录的网站上查资料。

现成做法是给每个 Agent 一个浏览器工具（chrome-devtools、Playwright 的 MCP），每个工具各自启动浏览器，数量不受控。在小主机上，几个浏览器就能吃满内存和 CPU，拖垮中书和 Harness。

用户的判断（2026-11-09）：
- 中书要有一个自己管理的浏览器服务：控制窗口数量和排队，控制性能与并发，功能要全；
- 浏览器始终用一个独立的档案，保留登录状态（用户已定）；
- 名字叫「司门」，命令是 `simen`（用户已定）；
- 在司辰发布之后，单独一批做（用户已定）。

核实过的事实。实验环境：2 核 8 GB 的 Linux 主机，Debian 12 的 Chromium 156，容器内存上限 1.5 GB、CPU 1 核、只读根文件系统、去掉全部 capability。

- **资源。**
  - 内存：空闲约 180 MB。同时开着本地报告、东方财富、雪球、新浪四个页面，约 590 MB；关掉三个后回到约 270 MB。
  - CPU：重页面加载主要耗 CPU。东方财富单独加载 12 秒；和新浪同时加载 19 秒，与分别加载的总和相当。在 1 核上限下，多开窗口只能让大家互不等待，不会更快。
- **不开端口也能遥控。** 用 `--remote-debugging-pipe` 启动，就能完成全部操作：新开页面、导航、执行脚本、截图、设置设备尺寸、画面推流、鼠标点击、输入中文。全程不监听任何网络端口。
- **渲染。** 装了 Noto CJK 和彩色 emoji 字体后，中文和 emoji 正常。手机宽度的横向溢出和控制台错误都能测到。
- **沙箱。** 在默认容器安全策略下，Chromium 自带的沙箱起不来。在 Codex 容器策略的基础上，再允许 `chroot` 和带命名空间标志的 `clone`/`unshare`，就能带沙箱运行。
- **登录状态。**
  - 带有效期的 cookie，浏览器重启后还在；
  - 只在会话期内有效的 cookie 默认会丢；打开"继续上次浏览"（档案偏好 `restore_on_startup`）后也能保留。
- **档案锁。** 浏览器被强行结束后，档案里会留下一把锁，锁上记着旧主机名。换了容器，Chromium 就拒绝用这个档案。独占档案的服务在启动时要清掉旧锁。
- **反爬。** 东方财富、新浪正常。雪球从数据中心地址访问时要求"滑动验证"；把 UA 换成普通 Chrome、去掉自动化标记后，仍然要求。
- **认出对话。** DSH 运行 shell 命令时会设置 `DSH_SESSION_ID`（见 [ADR 0022](0022-sichen-time-module.md)）。Codex 程序里有 `CODEX_THREAD_ID`，但运行时是否设置还没核实。
- **端口风险。** 中书的 Agent 工具端点和 Harness 在同一台机器的回环上互通。如果浏览器把遥控端口开在回环上，Agent 就能绕过司门直接控制浏览器，还能一次读出全部 cookie。

## 决定（提议）

1. **独立模块「司门」，命令 `simen`。** 和司辰一样：
   - 有自己的目录和协议版本，命令行只用 Node 自带的库；
   - 命令按"类别 + 动作"组织，错误用中文说明，加 `--json` 时输出给程序读的格式；
   - 跟着中书一起构建和更新。
2. **浏览器是一个独立的原生服务，不放进中书的镜像。**
   - 一个实例只有一个浏览器进程、一个持久档案（用户已定）；
   - 档案只放在浏览器服务那边，不在任何工作区里，Agent 读不到档案文件；
   - 浏览器能只读地看到工作区，用来打开本地报告。
3. **只用管道遥控，不开端口。**
   - 浏览器那边运行司门的一小段宿主程序，它用 `--remote-debugging-pipe` 启动 Chromium，再把这条通道以 unix socket 只交给中书；
   - Agent 只能走 `simen` → 中书 → 宿主这一条路；
   - 宿主负责：启动时清掉旧锁、打开"继续上次浏览"、浏览器崩溃后重新启动。
4. **窗口和排队由中书管。** 中书知道是哪段对话在调用，也知道这一轮什么时候结束。
   - 窗口上限按实例配置，建议默认 2 个；
   - 一段对话最多占一个窗口，靠 `DSH_SESSION_ID` 认出，同一段对话的连续命令都用这个窗口；
   - 窗口满了就先来先得地排队，命令行显示前面还有几个；等太久（建议 5 分钟）就明确失败，不无限等；
   - 窗口在三种情况下收回：那段对话这一轮结束时；闲置超过 3 分钟；有人在排队而一次占用超过 15 分钟；
   - 浏览器重启后所有占用作废，命令行说明要重新打开。
5. **资源有硬上限。** 浏览器服务的内存、CPU 和进程数由实例限制，建议 1.5 GB、1 核、512 个进程。超出上限时只伤到浏览器自己，不会拖垮中书和 Harness。
6. **功能要全。** 首批命令：
   - 打开：`open`（网址或工作区里的文件）；
   - 看：页面文字，和带编号的可操作元素清单；
   - 操作：`click`、`type`、`press`、`scroll`，按编号或按选择器；
   - 脚本：`eval`；
   - 截图：`shot`，写到命令所在目录；
   - 尺寸：`viewport`，电脑或手机预设，也可以写宽×高；
   - 其他：`console`、`close`、`status`、`doctor`。
7. **登录窗口：由用户亲手登录。**
   - 中书网页里有一个只有管理员能打开的「浏览器」页面，能看到实时画面，可以点、滑、输入和改网址，用来登录和通过人机验证；
   - 它占一个窗口，排在 Agent 的排队前面；
   - 司门不自动破解验证码，也不替用户输入密码。
8. **对网站表现为普通 Chrome。** 不带 `HeadlessChrome` 字样和自动化标记。实验表明这挡不住雪球的验证，但能少触发一些拦截。
9. **登录过的网站有安全边界（待用户确认）。**
   - 在已登录的网站上，Agent 能做用户本人能做的事；网页内容也可能诱导 Agent 去做。
   - 提议：只登录查资料用的网站，不登录券商、银行和支付网站；实例可以配置一份"禁止打开"的网址清单，司门拒绝打开清单里的网址。
10. **安装与体检。**
    - Chromium 版本固定在浏览器服务的镜像里，随实例更新；
    - `simen doctor` 和实例体检会报告浏览器版本、窗口、排队和内存。
11. **首批只接 DSH。** Codex 要先核实对话编号和沙箱里的网络，再接入。

## 取舍与后果

- **为什么不直接给 Agent 浏览器 MCP 工具：** 数量控制不了；MCP 调用认不出是哪段对话（ADR 0022）；遥控口暴露在外。
- **为什么不用现成的浏览器服务（如 browserless）：** 它按连接分配会话，连接一断会话就结束，做不到"一段对话连续用同一个窗口"；它的许可证也有商用限制。
- **为什么始终用一个档案：** 这是用户的决定。代价是：所有窗口共用登录，Agent 在这些网站上就等于用户本人；档案进入实例备份，备份里也就有登录凭据。
- **为什么排队放在中书里：** 中书能按"这一轮结束"来收回窗口，宿主可以保持简单。
- **为什么要放开容器策略里的几个系统调用：** 浏览器打开的是不可信的网页。宁可多放开两项系统调用，也要保留 Chromium 自己的沙箱，不用 `--no-sandbox`。
- **更新负担：** 浏览器镜像约 1.5 GB，Chromium 需要跟着安全更新。
- **雪球这类站点要有人帮忙：** 人机验证得用户在登录窗口里亲手做。滑动一次后能保持多久，还没验证。

## 未决与待验证

- 待用户确认：
  - 安全边界：登录哪些网站，是否要"禁止打开"清单；
  - 登录窗口是否首批就做，以及在手机上怎么操作；
  - 窗口数、等待时间、收回时间这些默认值。
- 待验证：
  - 用户通过登录窗口亲手滑动后，雪球能否放行、能保持多久；
  - Codex 能否接入；
  - 登录窗口在手机上好不好用。
