# 读取不产生变化，运行中的输出只推新增内容且不落盘

## 背景与依据

2026-11-08，用户评估第一版时，在测试实例上用真实浏览器和真实 Codex 测量了同步开销。同一段对话连问两轮，每轮回答约 1,800 字：

| | 第 1 轮（对话很短） | 第 2 轮（对话长一倍） |
| --- | --- | --- |
| 回答本身 | 5.2 KB | 5.1 KB |
| 推送帧 | 229 条 | 218 条，共 616 KB |
| 整份快照重读 | 74 次，共 304 KB（平均 4.1 KB） | 66 次，共 677 KB（平均 10.3 KB） |
| 变更表写入 | 228 行 | 217 行 |

开着对话闲置时只有阅读续租和心跳，符合设计。但发起任务后切到设置页，任务结束后页面每 555 ms 重读一次快照，30 秒 52 次、722 KB，直到回到对话页才停。正式实例上看到的间隔约 560 ms，原因相同。

原因有三处：
- **读取会产生变化。** 打开一段没人观察的对话时，会新建运行时读取原生最新页。新运行时没有“上一页”可比，于是写一条变化；变化又让页面再读。网络往返超过运行时 250 ms 的释放时间，这个圈就会一直转下去。
- **实时帧带的是全文。** 每 40 ms 一帧，每帧都带这条输出到目前为止的全部正文，推送量随回答长度的平方增长。
- **每帧都触发整份重读，而且每帧都落盘。** 页面收到带正文的帧后照样重读快照，快照随对话变长。每次增长都写进变更表，数据库每次提交都要等硬盘写完（`synchronous=FULL`）。

这些都是成熟做法的偏差，不是新问题：
- 命令与查询分离（Bertrand Meyer，1988）：查询不改变可观察状态。
- 数据库复制与消息日志：消费者从自己的位置接着读，落后太多时先取快照，再重放快照之后的日志。
- 流式模型接口：每帧只带新生成的文本。

## 决定

1. **读取不产生变化。** 每段对话持久保存一个原生最新页标记（页的摘要，或 `error:<代码>`）。读到原生最新页后，只有标记与已存的不同，才更新标记并写一条变化，两步在同一事务里完成。运行时释放、服务重启后再读到相同内容，都不再通知。
2. **运行中的增长不是持久事实。** 实时条目在内存中的实时流上发送，不写变更表、不排队，也不能按游标补发。每帧带本进程的纪元（epoch）和递增序号（sequence），页面据此发现漏帧。心跳带当前序号，用来发现最后一帧丢失。
3. **只发新增。** 正文和工具输出按“上次发出后追加的部分”发送（`at` + `append`）。不能表示为追加时（例如被改写）发整段，单帧超过上限时发“已省略”标记，由快照取回。
4. **页面就地应用，不再逐帧重读。** 页面把帧接到本地条目上，更新的条目保持原位置。只有这些情况才重读快照：持久变化、发现漏帧（序号不连续或心跳超前）、断线重连、帧接不上本地内容。快照标明自己已包含的实时位置，页面先装快照，再重放其后收到的帧；已包含的帧跳过。
5. **持久变更流照旧。** 状态、操作与回执、排队、提问与审批、用量、本轮文件、未读、列表摘要和原生最新页标记的变化，仍写变更表，带稳定 id，可按 `Last-Event-ID` 续传；[ADR 0004](0004-recoverable-communication.md) 的契约不变。

## 与既有决定的关系

- 细化 [ADR 0004](0004-recoverable-communication.md)：“持久事件、可补齐”只适用于持久事实。运行中的增长明确是临时的，恢复靠快照加重放，不靠事件补发。
- 修改 [ADR 0014](0014-native-history-source.md) 中“Store 只记录变更提示（可带条目身份）”：实时增长不再写变更提示；Store 另外记录每段对话的原生最新页标记，不含正文。

## 取舍与后果

- 推送量和硬盘写入只随真正新增的内容增长，不再随回答长度和对话长度相乘。读取变成纯查询，空转的根源消失。
- 页面在帧之间以本地内容为准，正确性依赖序号、快照位置和追加偏移三者一致。为此加入了漏帧检测、快照加重放和“接不上就重读”的兜底。
- 发布后，浏览器里仍在运行的旧版页面不认识实时帧：运行中看不到逐字输出，只在状态变化时刷新，刷新页面后恢复。
- 持久变化仍会触发整份快照重读（每轮约个位数次），快照大小仍随对话变长。增量快照留待以后按测量决定。
- 子 Agent 过程的增长仍写变更提示，按“关注”订阅（用推送连接本身代替阅读租约）也留作后续。两项都不在本决定范围内。

## 替代方案

- **保留“通知 + 整份重读”，只加节流。** 实现最省，但每次重读的成本仍随对话长度增长，节流还会让输出变得一卡一卡。
- **改用 WebSocket。** 现在的流量以服务端到页面为主，SSE 已经够用，换通道解决不了数据量的问题。
- **直接转发原生的增量事件。** 会把 Codex 和 DSH 的事件差异带出 adapter。在服务端按“上次发出的内容”计算追加，对两个 Harness 一致。

## 验收

- 自动化：读取不变的历史不通知、标记跨重启有效、实时增长不写变更表、帧带追加内容、超大帧省略、慢连接被踢且不排队、页面打补丁的各种边界。
- 测试实例：用真实 Harness 重做上面的测量，对比推送量、快照重读次数、变更表写入和“切到设置页后任务结束”的空转。
- 本 ADR 为草案。用户 2026-11-08 要求实现并在测试实例重测；结论确认后改为 accepted。
