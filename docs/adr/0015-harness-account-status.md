# 中书检测两端的 Harness 账号状态，Codex 可在设置中用设备码续登

## 背景与依据

2026-11-07，用户准备在远程服务器上长期使用中书。Harness 账号由各自的原生系统管理，中书无法替它续期；用了一段时间后，某一端可能需要重新登录。此前（2026-11-02）登录由操作者在仓库之外用维护命令完成，再把授权链接交给用户，产品本身不提供入口。用户在对齐中确认改为：中书检测并提醒两端的账号状态，Codex 可以在中书内续登，DSH 仍由操作者处理。

在固定兼容版本上对照源码核实（未在真实 Host 运行）：

- Codex App Server 提供设备码登录：返回验证地址和用户码，用户在任意设备的浏览器上完成，完成后 App Server 发出通知。
- Codex 的账号读取只说明本地有没有凭据。读取时可以要求先刷新，但刷新失败不会体现在读取结果里。中书目前只用“有账号”判断可用，所以凭据已无法续期时，要等任务失败才会暴露。
- Codex 的额度读取会访问厂商服务，可以作为凭据仍然有效的探测，有待实测。
- DSH 的账号凭据没有过期和刷新流程。平台拒绝凭据时，Host 清除它，状态变为未登录，并通过过期通知流告知。
- DSH 的登录回调只接受带显式端口的本机回环地址。手机或经公网访问的浏览器都无法直接完成登录。

依据：[Codex 账号协议](https://github.com/openai/codex/blob/rust-v0.166.0-alpha.5.1/codex-rs/app-server-protocol/src/protocol/v2/account.rs)、[Codex 账号处理](https://github.com/openai/codex/blob/rust-v0.166.0-alpha.5.1/codex-rs/app-server/src/request_processors/account_processor.rs)、[DSH 账号接口](https://github.com/deepseek-ai/deepseek-harness/blob/504a01a9578abc2c6f1fb896b1dc322c9fe24f66/packages/api/account-controller/src/index.ts)、[DSH 账号登录与凭据](https://github.com/deepseek-ai/deepseek-harness/blob/504a01a9578abc2c6f1fb896b1dc322c9fe24f66/packages/credentials/deepseek-account-platform/README.md)。这些是协议依据，不替代目标版本的真实验证。

## 决定

- **账号状态。** 设置中提供 Harness 账号区，每端显示连接、登录和最近一次核实的结果。结果至少区分：Host 未连接、未登录、凭据被拒绝或无法续期、有效、暂时无法核实（例如网络失败）。只有本地凭据不能算作有效。
- **提醒。** 某一端需要处理时，中书在界面上提醒；离开页面时的推送按 [ADR 0018](0018-push-notifications.md)。
- **Codex 续登。** 管理员可以在中书发起设备码登录。页面显示验证地址和用户码，等原生发出完成通知后重新核实；登录可以取消，同一时间只有一个登录尝试。
- **DSH。** 只检测和提醒。重新登录仍由操作者在仓库之外完成；中书不代理、不转发 DSH 的登录回调。（2026-11-07：用户决定 DSH 也在页内重新登录，并在账号区提供 DeepSeek 官方的用量与充值链接。DSH 登录完成后会跳到 Host 自己的本机回调地址，浏览器打不开时，用户把这个地址粘贴回中书；中书只取出其中的 code 和 state，在服务器上交给 Host 自己的 `/oauth/callback`，不访问粘贴的地址本身。依据：原生回调只校验 state，并用 Host 持有的 PKCE 完成兑换，不依赖浏览器或来源。粘贴的地址不入库、不写日志。）
- **安全。**
  - 只有管理员会话能看到账号区和发起登录；发起与取消经来源和 CSRF 检查。
  - 用户码和验证地址只返回给发起登录的页面，不写日志，不入库。
  - 登录的发起、成功、失败、取消作为关键操作记录，记录里不含凭据。
  - 中书不读取、不保存、不导出厂商凭据，凭据仍由各 Harness 在自己的数据目录里持有（[ADR 0001](0001-native-harness-boundary.md)、[ADR 0006](0006-auth-session-data.md)）。

本决定替代 2026-11-02 安排中 Codex 登录只由操作者完成的部分；DSH 登录的安排不变。

## 取舍与后果

| 被放弃的方案 | 原因 |
| --- | --- |
| 继续只由维护命令登录 | 掉登录时用户不知道，离开电脑时也续不上 |
| DSH 也在页内续登（把浏览器里失败的回调地址粘贴回中书，由服务端转给 Host） | 原生明确不支持非回环回调，要依赖它没有承诺的行为；DSH 凭据又极少失效。（2026-11-07 改为采用：回调由中书在服务器上以回环地址交给 Host，没有使用非回环回调，见上方 DSH 一条） |
| 由中书持有并刷新厂商凭据 | 越过原生边界，扩大中书保管的秘密 |

后果：

- 中书多了一个能把厂商账号绑定到实例的入口，管理员会话的安全因此更重要。
- 两端的账号接口要随原生版本升级复核。
- 额度探测是否可靠、刷新失败在原生中的实际表现，需要在实现时用真实 Host 证明。
