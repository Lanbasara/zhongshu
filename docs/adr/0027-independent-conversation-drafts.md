# 新对话以独立草稿为入口，首发才绑定正式对话

## 背景

2026-11-13，用户确认「新对话」每次都应打开一份可编辑的新草稿，旧草稿有明确的续写入口。页面地址应能区分正在编辑的草稿与已创建的对话。

原有地址 `#new:` / `#new:<工作区>` 只定位到浏览器里的工作区草稿槽。同一槽还保留首发的配置和待核对状态。删除服务端对话后，本地槽仍可能指向被删对话，再点「新对话」就回到那次首发。在没有该草稿的浏览器中，同一工作区仍可新建。首发去重所需的稳定身份只需约束那一次提交。

## 决定

- **草稿 ID 定位本地编辑内容。** 每次点击全局或工作区的「新对话」都创建独立草稿，即使该工作区已有一份首发待核对的草稿。每份草稿有稳定地址，例如 `#draft/<草稿ID>`，在该草稿仍可恢复的浏览器中，刷新、前进和后退均按该地址恢复同一份。「继续草稿」用来主动返回旧草稿。切换工作区是编辑草稿的属性，草稿身份保持稳定，配置与材料仍按目标工作区核验。
- **对话 ID 定位服务端对话，操作 ID 定位一次首发。** 编辑阶段只有草稿身份。首次发送时，先在草稿中记录目标对话 ID 和操作 ID，固定配置与材料，再发起创建请求。创建、派发和恢复沿用这组身份。首发确认后，当前草稿页交接到正式对话，继续使用已有的 `#<对话ID>` 地址。沿用 [ADR 0010](0010-draft-first-conversation.md) 的创建边界和 [ADR 0004](0004-recoverable-communication.md) 的回执契约。
- **待核对状态只属于发起提交的草稿。** 结果未知时，重试核对同一目标和操作。新草稿可独立编辑和发送，旧提交的迟到结果只更新它自己的状态。配置核验明确失败且首发未派发，或目标对话已确认删除时，用户可显式将留在浏览器中的输入带入另一份可编辑草稿。原提交的绑定不随输入转移，发送需要用户再次操作。普通 404 或回执丢失不足以确认删除。正式对话的管理仍按服务端的生命周期和执行状态判定，见 [ADR 0012](0012-conversation-lifecycle.md)。

## 后果

一个工作区内可以同时保留多份草稿，路由和本地恢复都需按草稿身份定位。草稿地址的可恢复范围取决于浏览器本地是否仍有该草稿，正式对话地址则按现有认证和授权读取。升级时须保留可恢复旧稿及其未决提交身份。DSH 的首发技能准备继续遵循 [ADR 0011](0011-dsh-prepared-session.md) 的有界复用与占用核验。
