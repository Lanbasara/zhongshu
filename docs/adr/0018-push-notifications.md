# 中书用只负责推送的 service worker 发送通知，不做离线缓存

## 背景与依据

2026-11-07，用户说明自己会在手机和电脑之间交替使用中书：在一台设备上发起任务后离开，之后可能换另一台设备继续。用户希望离开页面后，仍能知道任务完成、失败、Agent 在等回答或审批，以及 Harness 账号需要处理。用户以前做过 PWA，对它的价值存疑。用户确认采用“安装体验加推送通知”。

现状：已经有独立窗口的 manifest；没有 service worker；图标只有 SVG。

依据：

- 浏览器推送需要 service worker，但不要求把应用安装到设备上。Android 上不安装也能收到推送；iOS 要求先安装到主屏幕。
- 中书离开服务器就无法工作，离线缓存几乎没有用处，反而可能让旧页面去访问新版本的服务。

## 决定

- **安装体验。** 补齐各平台安装所需的图标，安装后以独立窗口运行；平台支持时，用应用角标显示未读数。
- **订阅。**
  - 每个浏览器或设备由管理员显式开启推送。
  - 订阅保存在实例数据库，可以在设置中查看和移除。
  - 推送密钥按实例生成，保存在实例私有数据中，不进源码，也不进镜像。
- **触发事件。** 对话完成、对话失败、Agent 在等回答或审批（[ADR 0016](0016-questions-and-approvals.md)）、Harness 账号需要处理（[ADR 0015](0015-harness-account-status.md)）。
- **最少内容。** 通知只说明发生了哪类事件，并提供对话入口；不包含消息正文、提问内容或文件内容。用户点开后，经正常认证再读取详情。
- **service worker 的职责。** 只处理推送和点击通知，不缓存页面或接口，不提供离线使用。

## 取舍与后果

| 被放弃的方案 | 原因 |
| --- | --- |
| 离线缓存页面 | 中书离线时什么也做不了；缓存会造成旧页面配新服务的错误 |
| 只做安装体验 | 离开页面后仍然收不到提醒，满足不了多端交替使用的核心需求 |
| 只在页面内提醒 | 同上 |

后果：

- 新增订阅数据和对应的迁移。
- 服务器需要能访问各浏览器厂商的推送服务。推送经第三方服务传递，内容虽然加密，仍只发送最少的信息。
- 推送密钥更换后，已有订阅全部失效，各设备需要重新开启。
