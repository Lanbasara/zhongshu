# 自动任务由原生 Harness 执行，中书负责看见、管理与叫用户

## 背景与依据

2026-11-08，用户希望中书在保持通用的前提下，成为可靠、舒适的主观交易助手，用于投资研究类工作区。用户此前用两样东西安排时间：

- 在本机 DSH 桌面版里，用原生自动任务做盘中检查点、远期复核和例行检查；
- 在一个提醒应用里放约 50 条提醒，调查、复核和操作混在一起。

对齐中用户确认：

- 定时让 Agent 干活，用原生自动任务；中书不另造调度器。
- 提醒应用只由 Agent 写入"需要用户本人动手的操作"，调查与复核交给自动任务；中书不读取提醒应用。
- 结果投递到哪由每个任务自己选：例行任务每次新开对话，跟进回到原对话。
- 条件盯盘、每日简报都只是任务：条件用自然语言写在工作区的计划里，由 Agent 判断；不另写盯盘脚本，token 成本可以接受。
- 通知是一句话摘要，点开直达完整结果；结果本身不能缩水。
- 用户确认一份计划后，Agent 可以一次建好一组任务；触发后自停、清理旧任务不需要再确认。

原生能力（DSH 0.2.2-rc.1，`@deepseek-ai/dsh-schedule`，对照已发布包的类型与说明）：

- 任务由宿主持久保存，宿主重启后仍在；每个重复任务只补最近一次错过的时点；到期时恢复冷会话。
- 时间写法：一次（延迟或绝对时点）、固定间隔、每天、每周、cron、rrule；钟表时间带显式 IANA 时区。
- 投递目标三种：已有会话；首次投递新建、之后复用；每次投递都新建。新建会话只能指定目录与 Agent 预设，模型和权限用宿主默认。
- Agent 工具：`schedule_create`、`schedule_list`、`schedule_view`、`schedule_edit`。
- 远程接口：列表、目录、单条读取、投递历史、新建、修改（含暂停、恢复和删除，用 `expectedUpdatedAt` 做冲突检查）、立即运行，以及 `schedule/changed` 变更通知。
- 投递回执只表示消息进入了会话收件箱，不表示模型已经执行完。
- Codex App Server 是否有可调用的自动任务接口，未核实。

2026-11-08 在预发实例上实测（DSH 0.2.2-rc.1、标准预设、完全访问）：

- 标准预设带上述四个工具，Agent 能在对话里自己建任务。
- 投递到一段没人在读的对话时，中书不显示运行中、不标未读，因此也不推送；Agent 的回复只在原生里。
- 被投递的指令在中书对话里不显示，只看得到 Agent 的回复。
- "每次新建"的目标默认落在宿主项目根目录，而不是发起对话所在的工作区；新建的会话不出现在中书。
- Agent 没有时区信息时，按 UTC 排定时间。

## 决定

1. **执行归原生。** 调度、持久化与投递由 Harness 负责。中书不实现调度器，不另存任务副本；任务、时间和投递回执以原生为准。首版只接 DSH；Codex 在有可调用、经核实的原生接口之前，不提供自动任务。
2. **中书让自动任务可见、可管理。**
   - 列出实例内的自动任务：下次时间、状态、投递目标和最近投递。按工作区和"结果投递到哪"分组；对话里显示投递到这段对话的任务。
   - 新建、暂停、恢复、立即运行、修改、删除，都调用原生接口，并带原生的修改时间做冲突检查。Agent 在对话里用原生工具建的任务，同样出现在中书。
   - 识别迟到与漏跑（例如宿主重启后补投），并在界面标出。
   - 运行配置只用原生能做到的（2026-11-08 用户决定）。“每次新开”只能选工作区和预设，模型、思考深度、权限用宿主默认。“首次新开后复用”可以选完整配置：中书先按配置建好那段对话，再让任务指向它。投递到某段对话的，沿用那段对话的配置。Agent 在对话里建的任务沿用原生行为，中书不另改。
   - 可以选一个技能。中书在指令开头写明“使用技能 …”，由 Agent 运行时加载；原生定时投递不展开 `/技能名`，所以技能必须允许模型调用。
3. **自动投递引起的运行，与用户发送的同等对待。**
   - 投递引起的运行计入执行责任：显示运行中；结束后按 [ADR 0012](0012-conversation-lifecycle.md) 计未读。完成本身不推送“已完成”——要不要叫用户由 Agent 用主动通知决定，否则例行巡检会不停打扰；失败、等待回答或审批仍按 [ADR 0018](0018-push-notifications.md) 推送。（2026-11-08 实现中按用户“例行巡检没事就不推”的决定细化。）
   - 这次运行的结果单独记录，不改动中书自己发出的消息的核对依据，避免“正在核对上一条消息”的判断被后来的运行打乱。
   - 被投递的指令在对话里原样显示，并标明来自哪个自动任务。
   - 原生为任务新建的会话，如果目录属于已登记工作区，就作为中书对话接入，归在所属任务下面，不逐条占用侧栏；目录不属于已登记工作区的，只在任务里显示，不提供执行入口。
4. **Agent 可以主动叫用户。** 中书给 Agent 提供一个通用的"叫用户"能力，内容是一句话摘要和结果位置（对话里的那一轮，可附工作区文件）。中书推送这句话，点开直达结果。结果完整留在对话和工作区里，通知不替代、不缩短结果。叫不叫、写什么，由 Agent 按工作区的约定判断。
5. **通知内容。** 部分替代 [ADR 0018](0018-push-notifications.md) 的"最少内容"：Agent 主动叫用户时，通知可以带这句摘要（有长度上限），它会出现在锁屏上。其他事件的通知仍按 ADR 0018，只带对话标题和固定文案。
6. **领域方法不进中书。** 下面这些都由工作区的 skill 和文件承担：
   - 跟踪、盯盘、简报、复核等用法；
   - "确认计划后一次建一组任务、触发后自停"之类的规矩。

   中书代码只认识自动任务、投递目标、运行、通知和时间轴条目。它不理解投资语义，也不接入任何特定的提醒服务。
7. **时间轴来自原生任务与工作区文件。** 日历和回看读取原生自动任务，以及工作区发布的时间轴文件。文件格式在[自动任务与日程](../spec/automations.md)切片确定；中书只读这个文件。

## 取舍与后果

| 被放弃的方案 | 原因 |
| --- | --- |
| 中书自建调度器 | 要重做持久化、补投、防重和恢复，与原生重复，还会改变 [ADR 0001](0001-native-harness-boundary.md) 的执行边界。唯一的好处是能覆盖 Codex，等 Codex 有需求时再评估 |
| 中书直接接入提醒应用 | 中书会变成特定业务的产品，还要在服务器上保存第三方口令。用户已决定提醒应用只由 Agent 写入操作提醒 |
| 专门的盯盘脚本或条件引擎 | 条件的灵活性比省 token 重要。条件用自然语言写在工作区计划里，由 Agent 在定时运行时判断 |
| 通知只带固定文案 | 例行和盯盘任务多，光看"已完成"分不出哪次重要。用户要求一句话摘要，点开直达 |

后果：

- 依赖 DSH 的自动任务接口。它仍是 rc 版本，升级后要重跑接入路径。
- 中书要新增这些部分：
  - 原生自动任务的读取与管理接口；
  - 对投递引起的运行的观察；
  - 自动新建会话的接入；
  - Agent 的"叫用户"通道及其推送。
- 摘要会出现在锁屏上，也会经过第三方推送服务（内容是加密的）。在意的设备可以关掉通知，或隐藏锁屏内容。
- 宿主重启后只补最近一次错过的时点，补跑的结果可能已经过时。Agent 要按投递时间自行判断；中书标出迟到。
- 自动新建的会话用宿主默认的模型和权限。无人值守的运行如果请求审批，会停在等待，中书按 [ADR 0016](0016-questions-and-approvals.md) 推送提醒。
- Agent 默认不知道用户的时区。按钟表时间触发的任务，时区要写在工作区约定里。

## 未决与待验证

- "叫用户"能力怎么接入：Harness 里的 Agent 如何调用中书，并标明来自哪段对话（MCP 工具或其他通道）；鉴权怎么做。
- 实例上自动新建会话的默认权限与模型，以及它们对无人值守运行的影响。
- 能否靠原生的变更通知和回执，在投递发生时就开始观察，而不是事后才发现。
- 被投递的指令在原生历史里是什么形态，中书如何可靠地把它和自动任务对应起来。
- 预发实例上出现过一次短暂的"待核实 / 原生状态不完整"，原因未查。
- Codex 的自动任务接口。
