# Workbench 按能力分岗位：前台不变，心脏摇铃，只许往下叫

## 背景与依据

2026-11-09 首版上线后，用户评估项目质量时决定暂停加功能，先重构。`src/server/workbench.ts` 有 1931 行、131 个方法、39 个内存字段，一个类同时管理工作区登记与维护、文件保存、草稿与新建、历史分页、发送与排队、子 Agent、提问与回答、归档与删除、阅读租约和实时推送。

难点不在行数，而在隐藏的连线：
- 同步一段对话后，同一个方法直接暂停队列、刷新子 Agent、安排读取提问、派发下一条排队消息。
- 判断能否释放一段对话的内存，要同时查看阅读租约、子 Agent 租约与刷新、正在创建、正在派发、未决操作、队列、提问和子 Agent 状态。
- 改任何一项能力，都要先读懂整个类。

用户的要求是：按成熟的设计思想重构，结构干净清晰，以后也保持干净，功能完全一致。2026-11-09 用户确认了下述方向。

采用的设计思想：
- 门面（Facade）：调用者看到的入口保持不变，内部组织可以变化。
- 信息隐藏与深模块（Ousterhout，《A Philosophy of Software Design》，2018）：每份状态只有一个主人，接口隐藏有价值的复杂性。
- 观察者与依赖倒置：核心只发布事实，由关心事实的模块自己决定怎么跟进。
- 分层只向下依赖，并由机器检查。

## 决定

1. **前台不变。** `Workbench` 仍在 `src/server/workbench.ts`，公开方法的名称、参数、返回值、错误码和行为都不变。它只负责组装各模块、转交调用、拼出对话快照、启动与关闭，以及每 5 秒一次的恢复巡检。
2. **每份内存状态只有一个主人。** 其他模块只能调用主人的方法，不能直接读写它的字段。
3. **分层。** 模块位于 `src/server/workbench/`，只能依赖更低的层。

   | 层 | 模块 | 负责 |
   | --- | --- | --- |
   | 5 前台 | `../workbench.ts` | 对外入口、组装、快照、启停与巡检 |
   | 4 岗位 | `creation` `execution` `queue` `readers` `transcript` `subagents` `requests` `workspaces` `lifecycle` | 一项用户能力的全部规则与状态 |
   | 3 心脏 | `observation` | 每段对话的内存运行时：原生事件、状态与最新页同步、实时帧、失联与恢复、释放 |
   | 2 名单与账本 | `gate` `ledger` `history` | 谁正占用、谁被围住；中书自己下过的操作；原生条目的展示与短期记忆 |
   | 1 绑定 | `bindings` | 对话的工作区与 Harness 是否仍然成立 |
   | 0 工具 | `tasks` `pages` | 后台任务追踪与关闭；原生分页、游标和展示条目的规则 |

4. **岗位与功能地图对应。** 新功能先回答“这是人能做的哪件事”，再决定放进哪个岗位。

   | 岗位 | 对应能力 |
   | --- | --- |
   | `creation` | 草稿、模型目录、新建对话（[conversations](../features/conversations.md)） |
   | `execution` | 发送、停止、回执核对、Plan、技能（[execution](../features/execution.md)） |
   | `queue` | 运行中排队与提前发送（[execution](../features/execution.md)） |
   | `readers` | 谁在阅读、未读与关注（[continuity](../features/continuity.md)） |
   | `transcript` | 更早的历史、消息里的工作区图片、对话可引用的文件（[conversation-usability](../features/conversation-usability.md)） |
   | `subagents` | 原生子 Agent 的查看与停止（[subagents](../features/subagents.md)） |
   | `requests` | 提问与审批（[ADR 0016](0016-questions-and-approvals.md)） |
   | `workspaces` | 工作区登记、移除、维护暂停与文件保存（[workspace-management](../features/workspace-management.md)、[workspace-files](../features/workspace-files.md)） |
   | `lifecycle` | 改名、归档、删除（[conversation-management](../features/conversation-management.md)） |

5. **心脏只摇铃。** `observation` 不引用任何岗位。岗位通过“参与者”接口订阅心脏发布的事实：
   - 铃声：运行时建立、原生提示、看到新条目、一次同步保存了状态、同一次同步写完用量与实时帧、同步结束且无待办、观察丢失、恢复完成、运行时释放。
   - 投票：还欠执行事实（需要继续观察）、有页面正在阅读、还有其他理由保留运行时。

   心脏需要向上调用的两处，由前台在组装时注入函数：失联后核对交给 `execution`，恢复未完成的新建交给 `creation`。同步过程中各岗位跟进动作的先后，与重构前一致。
6. **同层岗位默认互不调用。** 允许的连线写在边界检查的白名单里，目前只有三条：
   - `lifecycle → subagents`：归档、删除前确认子 Agent 已结束。
   - `lifecycle → readers`：删除时撤下阅读租约。
   - `queue → execution`：排队消息派发时沿用发送的引用核对与消息组装。

   新增连线需要修改白名单并说明理由。
7. **机器检查。** `scripts/design-boundaries.ts` 扩展到后端：检查 `src/server/workbench/` 各模块的依赖方向和同层白名单，单个模块超过 500 行即失败。规则随 `npm run build` 与 `npm test` 执行。
8. **新功能放哪。**
   - 每次同步后要跟进 → 实现一个铃声，不改心脏。
   - 需要让对话保持观察 → 投一票。
   - 新的“能不能接受新工作”的事实 → 放进 `gate`，并写明由谁写入。
   - 找不到对应岗位 → 新建岗位，同时新建或修改功能地图。

## 取舍

比较过三种形状：
- **只抽出子 Agent 和提问。** 改动最小，但同步与释放的隐藏连线仍在，下一个功能仍然要读懂全部。
- **按技术层拆**（存储、原生调用、计时器）。一项能力仍然散在每一层，新功能要同时改多个文件。
- **按能力分岗位**（本决定）。改动面最大，由前台不变、逐步搬迁和现有测试控制风险。

代价：
- 前台有约 50 个一行转交。这是保持入口稳定的成本，换来 HTTP 层与测试零改动。
- 参与者接口有十个左右的可选成员。它把原来散在代码里的连线列成一张明面清单，没有增加新的行为。
- 原来挤在一行的长代码会被拆开，总行数会增加。

不合并的相似物：对话阅读租约与子 Agent 观察租约形状相似，但服务不同的目的（未读与实时提示），各自留在所属岗位。

`workbench-store.ts` 与 `workbench-http.ts` 不在本次范围。

## 后果

- 先搬家，后装修：先把方法原样移入所属模块，每一步都运行类型检查与全部测试；排版整理单独进行。
- [架构地图](../architecture.md)的“对话与操作”边界改为指向本决定和模块表。
- 以后若要修改心脏，需要先说明为什么不能用铃声或投票解决。
- 用户路径的一致性由功能地图的独立执行验收证明，不只依靠单元测试。
