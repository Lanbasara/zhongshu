# Feature map 必须经独立上下文实际执行验收

## 背景

2026-11-02 用户指出：实现作者自己执行浏览器脚本并通过测试，仍不能证明给陌生 Agent 的 feature map 能让陌生 Agent 跑通；并明确要求本轮由两个独立上下文子 Agent 验证，之后也遵循这一原则。ADR 0005 已规定地图的读者是独立验证 Agent，却没有把读者实际执行列为交付关口。

## 决策

补充 ADR 0005，不改变文档类别或证据归属：新增或实质修改 feature map 的入口、前提、驱动、观察或清理方法时，必须由至少两个不继承作者聊天历史的验证 Agent 实际执行验收。可按 Harness 或场景分工；受影响的方法都要有独立执行证据，核心端到端旅程由两人在各自适用现场驱动。只改错别字、格式或不改变含义的链接修复无需重跑。

作者自测证明已运行的行为，独立执行另证明地图可用，两者不能互相替代。独立者从仓库合同与类别入口发现地图，使用独立测试数据、应用和浏览器上下文；可以获得地图列明的操作者配置与权限前提，不能依赖作者口头补步骤、旧聊天或旧成功结论来导航、确定预期或签收。阅读源码与运行通用检查不能替代用户路径执行。

具体执行与证据要求统一归 [功能地图共同入口](../features/README.md#独立执行验收)，不在每张地图复制。产品或地图缺陷由作者修复，再由独立者复跑受影响路径；前提缺失与尚未运行分别记录，不靠降低判据换通过。结论必须给出实际覆盖，不能把两人参与、部分分支或结构检查通过写成整图跑通。

版本、执行者独立性、场景分工、动作/观察、失败与修订、证据及清理结果留在 PR/CI 或仓库外实验记录；地图继续只记录当前可操作方法。`check:docs` 只证明结构与链接，不能检验上下文独立性或替人工签署运行结论。

## 后果

文档交付增加真实执行成本；两人可并行分工并复用合格现场，但不得用正在试用的实例代替隔离验证。不增加顶层说明或每张地图的验收状态字段。交付在证据不完整时必须明确未完成范围；未获得独立执行证据的方法不得宣称已跑通。
